01Коротко, в одном абзаце

Почти весь экран — это локальный зашифрованный кэш (SQLite на диске). Живьём из сети данные тянут два синк-канала: hub push (SSE из core) как основной live-путь и фоновый сборщик (polling-sync) как REST-гидрация/проверка/fallback; оба складывают ответы в кэш, интерфейс читает уже из кэша. Поверх этого: ИИ-провайдеры генерят тексты ответов по запросу, хаб «ядра» (ChatMuse) по желанию шлёт поток событий (для сообщений — уже с безопасно нормализованным телом, когда оно есть), а Волт и галерея — единственное место, что лезет в сеть на каждый показ. Money-цифры (спенд за 30 дней, чеки, счётчики) нигде не хранятся — они пересчитываются на лету из локальных таблиц. Главная находка по пути: пока приложение просто запущено, фоновый сборщик, похоже, помечает диалоги прочитанными на OnlyFans — без открытия чата (раздел ниже).

04Куда что течёт — по каждому куску

Для каждой поверхности: чем питается (чипы-цвета), насколько свежо, и важные нюансы. Файлы указаны на уровне модулей.

Рейл аккаунтов

Колонка моделей слева: аватар, точка авторизации, бейдж непрочитанных, кнопки $ / ⚙.
кэш БД вычисляется OFAPI · 1 раз при старте

Имя, @ник, аватар читаются из таблицы accounts при каждом рендере. Бейдж непрочитанных — это сумма SUM(chats.unread_count), считается в SQL на лету. Первоисточник — единственный вызов GET /accounts при запуске.

⚠ Зелёная/красная точка авторизации — снимок на момент запуска: метод обновления статуса в коде ни разу не вызывается, так что до перезапуска точка «застывшая». См. находку №2.

Список чатов / инбокс

340px-колонка: фан, превью последнего сообщения, непрочитано, типсы, спенд за 30 дней, фильтры, поиск.
кэш БД вычисляется
Свежесть: всё из кэша — ни одного сетевого вызова на рендер

100% локально. Строки, lifetime-спенд (JSON в fans), спенд за 30 дней (SQL-сумма net по локальным транзакциям с плавающим отсечением), превью, непрочитано, «ждёт ответа» — всё из таблиц chats / fans / fan_transactions, которые наполняет сборщик.

Тред переписки

Сообщения, медиа, PPV (закрыто/куплено), типсы, статус SENT/SEEN, «печатает…», присутствие.
кэш БД вычисляется хаб: сообщения/typing/присутствие

Каждый пузырь (текст, статус PPV/isOpened, медиа, типсы, тумбстоны) — из кэшированной таблицы messages. PPV-чип и статус отправки выводятся производно. В hub-live входящие/исходящие message-кадры с нормализованным телом попадают сюда пушем без фонового GET /messages; id-only/notification-кадры и read-state остаются REST-проверкой. «Печатает…» и присутствие приходят пушем по хаб-SSE с коротким TTL (last-seen в шапке — кэш).

Композер · отправка · outbox

Черновик, оптимистичные строки, [NEXT]-цепочки, запрещённые слова, unsend, подтверждение отправки.
кэш БД вычисляется OFAPI · по действию человека

Видимый UI (оптимистичные строки, черновики, гейт «можно отправлять») — из кэша + производно. Единственная сеть — явные действия человека в send/engine.ts: отправка (POST), read-only верификатор, unsend, «печатает», mark-read; каждое срабатывает раз и пишется обратно в кэш. Send никогда не ретраится автоматически (инвариант SPEC §15).

ИИ-док

Reply / Improve / Deep / Ping / Hi: сгенерированные ответы, стриминг, тон, коучинг.
ИИ · live на прогон контекст: кэш контекст: live при нехватке

Любой текст — свежий live-вызов LLM на каждый прогон. Исключение — «саммари фана»: берётся из локального кэша summaries или из префетча хаба. Контекст (транскрипт, спенд, имя/био) — сначала из кэша, при коротком окне дотягивается live из OFAPI. Расход токенов пишется локально (ai_spend_log).

Модели по фичам настраиваемы: Claude (Sonnet/Opus/Haiku) и через OpenRouter — Gemini/Grok. Промпты заморожены byte-for-byte.

Панель фана

Инфо (профиль, подписка, био) и Скан (ИИ-саммари переписки).
кэш БД OFAPI · ≤1 при открытии, если устарело скан: ИИ хаб: синк саммари

Вкладка Инфо — OFAPI-происхождение, отдаётся из кэша fans; максимум один near-live getUserByUsername при открытии чата, если строка старше 5 минут. Вкладка Скан — вывод LLM в кэше summaries; хаб только best-effort синхронизирует тело саммари между устройствами — не источник профиля или денег.

Доска спендеров + статистика

Полки тиров (списки OnlyMonster), $-цифры, счётчики, бары выручки, радар реактивации, очередь «ждут ответа».
OFAPI · тиры live (мемо 5 мин) вся статистика вычисляется кэш БД

Полки и ростеры тиров — live OFAPI user-lists по запросу, мемоизируются в памяти на 5 минут. А вот каждая $-цифра, счётчик, точка тишины и вся колонка статистики — 0 кредитов, считается SQL-джойном по локальным таблицам fans / chats / messages / fan_transactions. Хаб не участвует.

Волт · галерея · выбор PPV

Медиатека модели, альбомы, галерея чата, прикрепление PPV с ценой.
OFAPI · live на каждый показ только пиксели превью: кэш
Свежесть: вживую — единственная поверхность без слоя БД

Уникально среди всех: query:vault.* и chat.gallery идут прямо в OFAPI на каждый рендер, 1 кредит/вызов, тормозятся только staleTime React Query (30/60/15с). В БД эти списки не кэшируются. Кэшируются лишь пиксели тумбов — через протокол media://.

Все тумблеры, маппинги аккаунт→страница, URL хаба, API-ключи, язык/масштаб/тема, бюджет кредитов.

вычисляется в памяти кэш БД (логи) liveness: SSE (off по умолч.)

Ни одного live-вызова OFAPI на открытие. Цифры — снимок локального счётчика кредитов в памяти (снимается как побочка любых других OFAPI-вызовов), локальные агрегаты (credit_log, ai_spend_log, outbox) и, если hub настроен, chatter-scoped сводка core /api/v1/ofapi/credits/summary по назначенным страницам. 05Находка №1 — диалоги читаются сами

⚠ Пока приложение запущено, чаты помечаются прочитанными — без открытия

Вердикт: очень вероятно · нужен 2-минутный тест, чтобы добить до 100%

Симптом (наблюдение владельца): диалоги становятся прочитанными сами по себе, просто пока приложение работает — фан видит «просмотрено», счётчик непрочитанных обнуляется, хотя чат никто не открывал.

Механизм — две связки:

  1. Сторона OFAPI. По вендоренной доке, сам запрос «получить сообщения» помечает чат прочитанным как побочный эффект. Прямая цитата из описания эндпоинта mark-as-read в openapi.json:
«Mark a specific chat as read. Alternative to List Chat Messages endpoint, if you just want to mark the chat as read without fetching messages.»

То есть отдельный mark-as-read существует ровно для случая «пометить прочитанным без фетча» — а значит обычный фетч сообщений помечает читанным заодно.

  1. Наша сторона. Фоновый сборщик сам зовёт listMessages (GET) по неоткрытым чатам: tail-fetch на каждой дельте каждые 20–60с (polling-sync.ts), поллер недогруженного медиа, и — самый крупный путь — backfill спендеров (один GET на каждого фана ростера, spenders/refresh.ts). Фан написал → через минуту сборщик «прочитал» тред.

Галочка «помечать прочитанным при открытии» тут ни при чём. Она по умолчанию выключена и гейтит только явный POST mark-as-read для открытого чата. Фоновые GET её вообще не смотрят — поэтому даже с выключенной галочкой, если связка №1 верна, чаты всё равно помечаются читанными. Это тихо ломает заявленную в коде инвариант «STRICTLY READ-ONLY toward OFAPI»: наш код сам mark-as-read не зовёт, но GET читает за нас.

Почему «вероятно», а не «точно»: код-половина доказана полностью; OFAPI-половина следует из формулировки доки косвенно (у самого GET в описании про read-state молчок). Наблюдение владельца сильно это подтверждает, но решающим будет изоляционный тест.

Решающий тест (~2 мин, ~3 кредита): при закрытых приложении и OnlyMonster (чтобы исключить, что читает OM) взять фана с непрочитанным входящим → дёрнуть только GET .../messages?limit=10 → через 5с глянуть GET /chats: упал ли unreadMessagesCount в 0 / сдвинулся ли lastReadMessageId. Упало после одного GET → подтверждено. Нет → опровергнуто (читает только явный POST).

Как чинить, если подтвердится: детектить «новое сообщение» по полезной нагрузке GET /chats (там уже есть lastMessage, unreadMessagesCount, lastReadMessageId) и не тянуть тело до реального открытия чата. Минус — текст и медиа неоткрытых чатов будут недоступны до открытия; backfill спендеров сделать строго opt-in с предупреждением. Это архитектурное решение и требует пере-проверки на живом аккаунте — занесено в TODO.md.

06Прочие находки по пути

№2 · Точка авторизации «застывает»

Зелёная/красная точка у аккаунта в рейле — снимок на момент запуска. Метод обновления статуса (accounts.setAuthState) в рантайме ни разу не вызывается, а событие хаба только запускает перечитывание той же неизменной строки. Итог: если аккаунт разлогинится во время работы, точка останется зелёной до перезапуска.

№3 · Волт стоит кредитов на каждый показ

Волт и галерея — единственная поверхность без слоя БД: каждый показ = реальные OFAPI-вызовы (1 кредит каждый), тормозятся только staleTime. Не баг, но стоит держать в голове при оценке расхода кредитов — частое открытие Волта это прямые деньги.

№4 · Рассинхрон SPEC ↔ код

SPEC §3 говорит про markAsReadOnOpen «default ON (decided 2026-06-10)», а код ставит false («P3 strictly read-only»). Поведение определяет код (безопаснее), но доку надо поправить, чтобы не путать.

№5 · Money считается, а не хранится

Спенд за 30 дней, чеки, доли по тирам, бары выручки нигде не лежат готовыми — это SQL-агрегаты по локальной таблице fan_transactions (rolling-окно 30 дней). Дёшево (0 кредитов), но значит: точность money завязана на полноту локального кэша транзакций.
